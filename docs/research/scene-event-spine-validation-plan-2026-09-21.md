# Scene 内の出来事・演技・Camera をつなぐ次段の検証計画

作成日: 2026-09-21
状態: 計画。実装・全編 H3 生成は未着手。

## 判断

次は Arc の本数や再試行回数を増やすより、**Scene の一回の出来事を内部 Shot 間でどう進め、どの瞬間を Camera が見せるか**を揃える。まず同じ 8B・同じ seed の短いオフライン比較で採否を決める。追加 LLM task の全曲常時実行は、この時点では採用しない。EMD に大きな改善が見えても、全編動画の前に短区間の H3 で一度だけ実画面を確認する。

「slot 分割そのものが悪い」とはまだ断定しない。現行にも Scene 単位の Cue Card（対象、配置、可視展開、身体主導、終端）がある。しかしレイアウト確定後は `_priority_cue_phase` 等の短い役割名で Shot へ配り、Action を slot ごとに生成し、その確定後に Camera を選ぶ。Scene 全体の**一度限りの転換点、前 Shot の具体的な終了状態、次 Shot で見せる部分**は共通の時間軸として固定されていない。Camera の `COVERAGE` は環境・全身・上半身と手・顔・結果の五分類で、歌詞対象と接触点の可視性を直接保証しない。形式上の成功と映像上の脈絡は別である。

旧 `cl-japanese2json` は同じ Scene 応答に複数の時系列 ACTION と COMPOSITION、外部効果、CAMERA を同居させ、8B では歌詞動作の先行設計も使っていた。その一体性が有力な差だが、旧版は Python による Action の再配分も行っていた。現行の AS IS 原則を保つため、その上書き処理は移植しない。旧版の演技・Camera の良さを全てこの構造だけに帰属させることもできない。

## 比較する最小構成

| 案 | 変更 | 利点 | 主なリスク |
|---|---|---|---|
| A: 現状 | 変更なし | 時間・文脈の基準 | 接触反復、対象の不可視、Shot ごとの再開始が残る |
| B: Scene 進行だけ | レイアウト確定後、Scene 内の全 Shot を**一括入力**し、一回の出来事の各段階と開始・終了状態を 8B に一括提示させる。採用した段階文を Action の各 slot に渡す | Shot 独立の生成を残しつつ、同一出来事の反復を防げる可能性 | 追加呼出し、長い Scene での出力欠落、Cue の誤認を増幅する恐れ |
| C: B + Camera 可視性 | 同じ段階文と「今回映す対象・身体部位」を Camera へも渡し、選択した `COVERAGE` と画角でその部分が見えることを構造検査する | Action と Camera が同じ転換点を撮る | 有限 Camera 語彙の拡張・構図矛盾の再試行が増える恐れ |

第一候補は B→C。Scene 計画を既存 Cue Card の九項目に無条件で追記すると、8B の行プロトコルと文脈負荷をさらに悪化させ得る。一方、新 task を先に決め打ちする必要もない。まず B を「既存 Cue の本文と Shot 長を使う、Scene 一括の短い出力」として小規模実験し、Cue Card の追加欄で同等の結果が出るなら追加 task を捨てる。比較時に**LLM 呼出回数、入力・出力 token、最長 context、再試行回数、推論時間**を両案で記録する。

必要な Scene 進行情報は、`Scene番号／現在歌詞の根拠／対象／一度だけ起こる変化／各Shotの役割・開始状態・終了状態／次へ見せる部分` に限る。接触しない歌詞、人物から独立した外部効果、間奏はそれぞれ「非接触」「自律現象」「演技と継続」のまま扱い、全 Scene を `接近→接触→解放` の固定型にしない。具体的な対象・動詞・位置・時系列文は LLM が作り、Python は slot 対応、重複・欠落、Cue の出典、禁止された対象の流入を検査するだけにする。自然文の補完・並べ替え・言い換えはしない。失敗時は問題を記録し、その候補を成功扱いして採用しない。

Camera 側は Action 確定後の現行順序を維持する。新しい Camera 推論段は作らず、同じ slot の進行情報と確定 Action を入力し、`COVERAGE` が必要な手・対象／顔・口／外部効果／全身を隠さないか検査する。既存五分類で表現できなければ、有限の coverage 値の追加を別途判断する。Camera が Action を書き換えることも、Python が対象名からカメラ文を創作することもしない。構造検査に通っても実際の H3 描画の可視性は保証されない。

## 検証順と停止条件

1. **P0: 基準を固定。** 9月21日の三 Scene オフライン証跡を保存基準とし、苔の一回の接触、狐火の自律移動、抽象歌詞の非物体化を照合する。加えて、実曲から複数 Shot の一 Scene と、接触対象のない間奏を各一つ選ぶ。同一モデル、temperature、seed、Cue、レイアウト、Shot 長、Compiler 設定で比較する。Action と Camera の原文、最終 EMD、コンパイル後 H3 prompt を slot ID で追跡する。
2. **P1: B を試す。** Scene 一括の出力が全 slot を満たし、選択済み Cue 以外の具体物を追加せず、同じ接触・出現・解放を複数 Shot で再実行しないかを見る。境界の開始／終了姿勢、対象の位置、外部効果の前後関係を人手で採点する。失敗を隠す fallback や Python の作文は入れない。
3. **P2: B に改善があった場合のみ C を試す。** 接触・変化の Shot で手と対象、反応 Shot で目と歌唱口を同時に見せる構図か確認する。顔寄りが早過ぎて対象を隠す、Arc の方向が継続中に反転する、Camera が前 Shot の終端画角を捨てる場合は失格。Camera の呼出回数を増やさず、既存の有限選択と検査を優先する。
4. **P3: 低コストの実映像確認。** B/C が EMD と H3 prompt の双方で明確に改善し、プロトコル安定性と予算を満たした時だけ、Scene Debug Splitter で当該一 Scene を同じ参照・音源・モデル・steps・seed で A/C 比較する。全編レンダリングは、その映像で対象・動作・構図の連動を確認してからユーザーが判断する。

オフライン採用の必須条件は、評価した具象 Scene で「一つの歌詞対象が Scene 内だけに現れる」「同一接触／効果開始を二度実行しない」「重要な変化を Camera が遮らない」、対照 Scene で「存在しない接触対象を作らない」、全件で「EMD・Compiler 完了」「AS IS と参照・Direction の境界を維持」である。単なる Arc 数、CUT/CONTINUE 比率、文量の増加は合格根拠にしない。品質の判定は一 seed の逸話で終えず、勝った構成だけ別 seed で再確認する。

## 計算費・文脈・運用上限

- 既存三 Scene 診断の Planner は約 **56.5 秒／31呼出し**（9月21日の保存証跡）。別条件の 9月20日比較は約37秒／28〜29呼出し。これらを 5060 の実行時間へ直接外挿しない。
- 新しい Scene 出力を試す場合も**全曲の歌詞・全Scene・全Camera履歴を再送しない**。現在 Scene の歌詞、採用 Cue、Shot 数・長さ、直前の終端だけに制限する。まず 1 Scene の短い出力上限を測り、形式違反の修復は一回までとする。
- `n_ctx=16384` では入力 token と予約出力、safety margin の合計を実測して必ず budget 判定する。短区間成功だけで約6分の楽曲へ一律適用しない。選択 Scene の Planner 時間増が概ね **30%超**、呼出し・retry が持続的に増える、又は context 超過が起きるなら新段の全曲採用を見送る。画質より先に 5060 での運用可能性を確認する。
- 実験機能はまず開発時の限定分岐とし、採用後も profile metadata から選択できる形を候補とする。UI パラメータや既存 WF の入出力、EMD／Compiler の契約は、オフライン合格前には変更しない。既存出力を黙って書き換えず、失敗と fallback は INFO/WARNING に区別して残す。
