# Scene Eventの対象選択：任意候補と作者固定指示の間

2026-09-24。これは`anime_scene_author_mv`経路の設計調査であり、本番Plannerの実装変更やH3映像の品質判定ではない。[P1短区間比較](shot-linkage-p1-candidate-comparison-2026-09-24.md)で、Scene 4の歌詞「人は花より／短く咲いて」を入力に含め、花の演出候補を加えても、試したseedでは落葉がEventに選ばれた。一方、8Bが花を表現できないという結論にはならない。[Planner v54の保存試験](planner-v54-lyric-cue-discovery-2026-09-20.md)では「参道に咲く花」から花びらの動きと人物反応が生成された。ただしこの歌詞は現在の比喩的な「人は花より／短く咲いて」より直接的であり、厳密な同条件対照ではない。[EMD 00014の評価](planner-emd-00014-event-role-review-2026-09-20.md)にも、現在と同じ花の歌詞で3 Shotに花が現れた記録があるが、その実行の生Event・Cue応答は保存されていない。成功能力と今回の選択失敗を分けて扱う。

## 現行経路で確定できること

| 入力の強さ | 経路 | 現在の結果・限界 |
|---|---|---|
| 作者固定の``* `演出` 本文`` | Template EMDの当該Shotに置く | 同一Sceneで一つでも固定EventがあればEvent LLM呼出しを省く。本文とShotはRendererが保持し、未指定の演技・Cameraだけを生成する。作者が決めた出来事を自動選択の成否に依存させない |
| 現在Sceneの原歌詞 | `original_lyrics`、試験時は`current_lyric_focus`もEventへ送る | Shotと時刻は入力されるが、Event応答は根拠となった原歌詞を返さない。Scene 4では「花」がShot 2に届いても背景の落葉を選んだ |
| ユーザーの`# 演出候補` | Directionから`staging_candidates_optional`へ原文を渡す | あくまで任意の着想。8Bが採用・変形・不採用を選べる。現行Scene Authorは候補をEventとPerformanceへ渡すが、採否の構造化記録はない |
| 背景・前Scene状態 | `scene_environment`、`scene_emd`、継続時の終端状態 | 配置と連続性の情報。主題の根拠ではないはずだが、今回のScene 4では紅葉・落葉が歌詞の花より優勢になった |

根拠は[`core/planner/scene_author.py`](../../core/planner/scene_author.py)の`fixed_events`分岐、`accepted_event`と`event_source`の受け渡し、[`core/planner/renderer.py`](../../core/planner/renderer.py)のtyped出力、および[`tests/test_scene_author.py`](../../tests/test_scene_author.py)の作者固定・候補伝達試験である。Eventの有限grammarは`EVENT<TAB>1<TAB>SHOT=番号｜本文`という輸送と存在するShot番号だけを拘束する。本文の対象がどの原歌詞に対応するかは検査しない。Shot番号が無効なら最大2回の要求になるが、**形式上有効な落葉Eventはそのまま採用され、後段PerformanceとCameraはその落葉を既成のScene出来事として読む**。Pythonが花へ書き換える経路はない。

作者固定と任意候補を混同しない。作者固定は「このShotではこれを描く」という命令であり、全自動Eventを置き換える。候補は「合うなら使ってよい」という創作材料である。候補を本番で暗黙の必須命令へ昇格させると、別の歌詞でも同じ対象や動作を反復する危険がある。反対に作者固定を単なる候補へ弱めるとユーザー介入を失う。**必要なのは第三の強制度ではなく、8Bが自動選択した理由と選択対象を短く明示し、後段へ同じ選択を渡す輸送契約**である。

## 推奨する最小設計：同一Event呼出し内の根拠宣言

Event担当の呼出し数は増やさず、応答を「根拠選択」と「可視の出来事」の二部分にする。例えば試験用の概念形は次の通り。これは**まだEMD文法ではない**。

```text
EVENT	1	SOURCE=LYRIC:shot2:line84｜FOCUS=花｜SHOT=2｜参道脇の花びらが風を受け、人物の前を横切る
```

`SOURCE`は、当該Sceneに実在する原歌詞行の番号、明示的に選んだ演出候補のID、又は`NONE`から選ぶ。候補IDは既存の候補一覧に順序付きで付ける輸送用番号で、候補本文は変更しない。`FOCUS`は8B自身が選んだ可視対象・暗示の焦点を短く記す。`SHOT`は出来事が初めて見える位置、末尾は8Bの自然文をAS ISで保つ。作者が`演出`を固定したSceneではこの自動Event呼出しを従来どおり省き、作者文を最優先にする。作者固定のないSceneで候補が採用されても、候補原文を完成EMDへ自動貼付しない。

Pythonが機械的に確認するのは`SOURCE`のIDが**現在Sceneの入力に存在すること**、Shot番号が有効であること、必要な欄が揃うことだけとする。`花`という単語の部分文字列検査、原歌詞の名詞辞書化、出来事自然文の書換えはしない。前者は「神社」に含まれる「社」のような偽陽性を生み、比喩・暗示も誤って拒否する。[既往の対象一致監査](scene-target-event-alignment-validation-2026-09-22.md)では8Bの引用形式自体が9/32しか規約を満たさず、`PASS`を品質保証には使えなかった。従って`SOURCE`は診断と後段の一貫した伝達のための**出典**であり、意味的な正解証明や全曲の停止ゲートではない。

後段PerformanceとCameraには、採用Event本文に加えて`SOURCE`・`FOCUS`・開始Shotを短い構造として渡す。ただし「花なら必ず接触」「名詞は必ず直接表示」とはしない。花を一瞬映す、花びらで短命を暗示する、人物の視線だけでつなぐ等の表現余地を残す。Eventが`なし`なら人物演技だけでSceneを成立させてよい。Candidateを採用した場合も歌詞にない対象の演出を一律禁止しないが、候補由来であることをtraceに残し、背景inventoryからの無意識な主題転用と区別する。

## 採用前の反証可能な試験

1. **P0・CPU**：今回のScene 4の生入力、花が出た既存の評価記録（EMD原本を取得できる場合は原本も）、苔・狐火、抽象的な歌詞、歌詞にない設備だけが背景にあるSceneを固定する。作者固定／候補／原歌詞／背景の出所を表にし、既存入力の欠落か選択の逸脱かを分ける。
2. **P1・短区間8B**：現行Event契約と`SOURCE/FOCUS`契約を同じScene入力・複数固定seedで比較する。花の判定は単語の有無だけではなく、選んだ原歌詞、花又は花びら等の可視関係、初出Shot、後段へ渡る焦点の一貫性を見る。苔・狐火、歌詞に具体物がないSceneも入れ、過度な直訳・接触強制・`なし`の消失を退行条件にする。まずEvent一呼出しだけを比較し、効果がなければ全曲生成へ進まない。
3. **P2・必要時のみ**：P1で対象採用と位置が改善した場合に限り、PerformanceとCameraへ構造化焦点を渡し、短い連続SceneでEMDを比較する。創作表現が硬直する、プロトコル再試行が増える、16k contextや5060で遅すぎる場合は不採用とする。H3全編はEMD上の改善を確認するまで不要。

期待する改善は「花を毎回強制すること」ではない。**8Bが歌詞・作者候補・背景のどれから主題を選んだかを可視化し、選んだ対象とShotを同じSceneの演技・撮影まで失わずに運ぶこと**である。ユーザーの固定Shot演出は引き続き最優先で、8Bの判断結果をPythonが自然文修復しない。現時点では実測前の設計案であり、P1の改善を約束しない。
