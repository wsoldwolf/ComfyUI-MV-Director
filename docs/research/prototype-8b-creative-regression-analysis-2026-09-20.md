# プロトタイプ8Bと現行Plannerの演出生成能力を再評価する

日付: 2026-09-20  
対象: EMD 00013、プロトタイプ8B／27B動画の埋め込みPlan、両プロジェクトのソース  
範囲: 原因分析と最小改修計画。今回はコード・プロファイル・WFを変更しない。

## 結論

**8Bでは花や狐火を想起できない、という診断は支持できない。現行Plannerの失敗をモデル規模へ帰属させる前に、生成契約と意味の受け渡しを修正すべきである。**

実際に旧8Bの最終プロンプトには、空を舞う狐火だけでなく、御神木の葉が揺れる描写も残っている。27Bには、大樹の根元の苔へ指先を触れ、撫でる一連の描写がある。したがって、語を認識する能力と、具体的な配置・動作まで発展させる能力を分けて評価する必要がある。

現行版の大きな問題は次の組み合わせである。

1. 歌詞からの逸脱を防ぐ規則が、歌詞に適合する創作的な補完まで禁止している。
2. Scene単位の厳密な局所化が、歌詞の文としての意味と継続演出を切断する。
3. 人物以外の出来事を、人物の身体演技に従属させすぎている。
4. 多数の短いShotへ個別に身体演技を要求し、同じ全身テンプレートへ収束している可能性がある。
5. 自動Cueの欠落を許す経路は存在するが、00013が実際にどの経路を通ったかは未確定である。

監査を10回へ増やすこと、新しい分類段をすべての歌詞行へ追加すること、意味品質の不合格をすべて停止条件にすることは、現時点の第一選択としない。

## 3. 現行契約で失っているもの

### 3.1 「根拠がある」と「歌詞に動作が明記されている」を混同している

[Visual Beatシステムプロンプト](../../prompts/timeline_planner_visual_beats_system_prompt.txt)は、対象名の存在だけでは常に`接触=禁止`とし、接触には同じSceneの歌詞又は作者本文の許可を要求する。

「昨日の願いは／苔へと還る」から、苔が存在することや変化することは許されても、「大樹の根元の苔を撫でる」は歌詞に動詞がないため禁止される。**これは8Bが連想に失敗する以前に、希望する演出が契約上不正になる問題**である。

灯籠へ無関係に触ることを防ぐ目的は正しい。しかし、次を別の判断にする必要がある。

- 対象の選択根拠: 現在の歌詞・作者指定にあるか。
- 具体化の自由度: 対象と意味に適合する場所、材質、動き、非破壊的な接触を補ってよいか。
- 禁止事項: 身体損傷、無関係な設備への接触、人物増殖、勝手な衣装変更など。

大樹の根元は歌詞の引用ではなく演出上の補完である。これを許すかどうかを明示し、引用された事実と同じfieldへ押し込まない。補完を許しても、特定の単語から固定動作を引く辞書は必要ない。

### 3.2 歌詞の意味単位とScene境界が一致していない

00013ではScene 6末尾に`御神木は`、Scene 7冒頭に`ただ葉を鳴らすだけ`がある。

一方、現行は根拠を現在Scene内の一つの原文行の連続部分に限定し、前Sceneの対象は次Sceneの歌詞が再度明示又は示唆しなければ使わせない。主語と述語が分かれた歌詞に対して、連続した「御神木が葉を鳴らす」という自然な解釈を難しくする。

これは前回提案した「各歌詞行を独立分類すればよい」だけでも解決しない。行単位の検出は補助にはなるが、意味の解釈は隣接する文節・一文・短い歌詞句で行うべきである。

同じ問題はCONTINUEにもある。対象の無制限な持ち越しを禁止することと、一つの出来事の余韻・結果を次の継続区間へ描くことは別である。対象に有効区間を持たせ、その区間内で一度開始して完結させる方が自然である。

### 3.3 独立effectが人物の演技に従属している

旧`lyric_visuals_light_8b`には、人物の身体動作とは別の`AUX_VISUAL`が存在する。9月11日時点でも、各Sceneに一つの実行可能な非人物の視覚変化を生成する明確な役割があった。

現行Visual Beatは外部自律effectを許す一方、「decorative effect alone is not a Beat」とし、人物の応答や身体の終端姿勢を要求する。[Actionシステムプロンプト](../../prompts/timeline_planner_actions_system_prompt.txt)も基本単位を人物のphysical performanceとしている。

そのため「狐火が空を横断し、奥へ回り込み、石畳へ光を落とす」という出来事だけでは完結しにくく、「その光を見ながら手を上げる」等へ吸収されやすい。この傾向はソースからの推測であり、00013の波紋反復の直接原因を証明するものではない。

必要なのは、すべてのSceneへeffectを強制する旧仕様の復活ではない。歌詞で選択された出来事について、人物動作・対象自身の動き・外部effectのいずれも主役になれるようにすること。人物は静止、視線、短い反応だけでよい場面も認める。

### 3.4 多様性の要求が全身テンプレートを生む可能性

現行は眼・頭・肩・胴体・骨盤・腕・手・支持脚・重心・高低差・終端シルエットを繰り返し要求している。00013では54 Shot中36に「右手を胸の前で広げ」、40に「体を左右に傾け」が現れる。

この一致だけで原因を断定できないが、歌詞の出来事より多数の身体条件を満たす汎用句へ最適化されている可能性が高い。禁止動作を増やすほど残った汎用句へ偏る危険もある。

同じActionプロンプト内には「有効対象のexact tokenをそのActionへ書く」と「毎Shotにtokenを機械的に繰り返さない」が併存する。Visual Beatにも「異なる具体cueを分配する」という指示と、対象を一つしか持たないCue Cardが併存する。小型モデルへ選択を委ねる前に、こうした指示の優先順位を一意にする必要がある。

### 3.5 共通Directionは渡っている。ただし加工され、役割が違う

[engine.py](../../core/planner/engine.py)の`performance_directions`は`camera`と`environment`を除いたDirectionをVisual BeatとActionへ渡している。Cameraには別のDirection集合を渡す。したがって「共通プロンプトが一切Plannerへ渡っていない」は現在の実装には当てはまらない。

ただしActionには環境inventory、シーン参照情報、全曲directionを直接渡さず、Cue Cardの配置・展開を経由させる。人物名簿もID中心で、詳細な外見はrendererの責務となる。漏洩防止には意味がある一方、Cueが失敗すると具体化の材料が減る。

[song-directionプロンプト](../../prompts/timeline_planner_song_direction_system_prompt.txt)は具体物・effect・人物動作の選択を明示的に禁止し、感情曲線と編集に限定している。これは旧Song Bibleのsectionごとの視覚モチーフとは同じ機能ではない。

解決は全Directionを全段へ無条件に追加することではなく、「対象として選んでよい情報」と「選択済み対象を具体化する空間情報」を区別して短く渡すことである。

## 4. 監査・自動Cueについての診断の修正

### 確認できた経路

- `_parse_cue_card`はfield構造、根拠引用、対象との包含関係等を検査するが、歌詞にあるすべての視覚対象を拾ったかは証明しない。
- automatic Cueは`valid`かつ対象が`なし`以外の場合にAction scopeへ登録される。
- 無効CueではAction用のraw beatを空にする経路があり、具体化要求が弱くなり得る。
- 対象なしで形式的に成立したCueも、取りこぼしを意味検査しなければ通り得る。

### まだ分からないこと

00013に対応するVisual Beatのraw response、Cue判定、Action初回候補、監査前後の採択候補を本調査では照合できていない。したがって、対象欠落が最初のCue選択、形式不正、Action転送、再試行時の置換のどこで発生したかは未確定である。

「透明な波紋」が最初の候補から履歴経由で広がったのか、共通入力から毎回生成されたのかも未確定。最終EMDだけから一方を断定しない。

旧`992fa8b`のPlannerには対象別の生成・検査・修復があるが、`audit`のコード検索から現行Action auditと同等の汎用監査段は確認できなかった。「旧版に監査LLMがあったから表現できた」とは結論しない。

### 前回レポートの位置付け

[00013評価](planner-emd-00013-automatic-cue-review-2026-09-20.md)の対象欠落・反復の観測は維持する。一方、そこで示した「歌詞行単位Cue Discoveryとfail-closed化が必要」という実装順位は本調査で見直す。

それらは欠落を発見・停止する方法であって、撫でる演技や独立effectを許可する方法ではない。矛盾した契約のまま監査と再試行だけ増やすと、5060向けの実行時間を悪化させる恐れがある。

## 5. 推奨する最小改修の順序

外部EMD、Compiler、H3 JSONの形式とAS IS原則は維持する。Pythonが名詞辞書から演技文を捏造・挿入する方式にはしない。

### P0: 矛盾した禁止条件を整理する

`anime_emotional_mv`のファイル側に、次の創作方針を持たせる。UIは増やさず、他プロファイルへ一律適用しない。

- 歌詞で選んだ対象には、文意と背景に適合する限定的な具体化を許す。
- 歌詞に接触動詞がなくても、選ばれた対象への非破壊的な接触を演出として選択可能にする。接触は必須にしない。
- 環境に存在するだけの設備は主対象にしない。灯籠禁止辞書ではなく、対象の出所で判断する。
- 人物・対象・effectのどれが動くかを選び、全要素を同時に動かす義務をなくす。
- 全身部位のチェックリストを各Shotへ課さず、その演技に必要な部位だけ具体化する。
- exact targetの保持をScene内の必要な箇所に限定し、毎Shotの反復義務と矛盾させない。

### P1: 既存Visual Beatを短い「出来事の設計」に寄せる

新しい全曲分類LLMを直ちに増設するのではなく、既存の一回のVisual Beat推論で、現在の歌詞句から何をどこに描き、何がどう変わるかを決める。

入力は現在区間に加え、文としてつながる前後の歌詞を少量だけread-onlyで与える。背景は選択した対象を置くための空間的条件として渡す。隣接歌詞を閲覧できることと、そこでの演出を重複実行することを分ける。

根拠となる歌詞範囲と実行するScene／Shot範囲を対応付け、同じ出来事を一度開始して完了させる。現在の単一対象契約の範囲でまず検証し、複数対象の取りこぼしが実測で残る場合にだけ、内部の出来事リストへ拡張する。

### P1: Shotを独立した別演技ではなく、一つの出来事の時間配分にする

対象確立、変化、反応、余韻のうち必要な段階だけを1〜3 Shotへ割り当てる。各Shotで接近・接触・反応・解放のすべてを再開させない。

長いArcや顔への遷移は、この同じ出来事と人物の状態を撮り続ける。意味がない短尺Shotの増加や、顔挿入ごとの全身演技の再生成を抑える。継続Sceneでは前区間の結果を引き継ぐが、開始動作を繰り返さない。

### P2: 修復は欠落した出来事に限定する

構造違反は引き続き停止・限定再試行の対象。創作上の改善は、入力歌詞と選択した出来事に照らして欠落・反復した区間だけを修復する。新しい全曲監査や全Shotの10回再試行を既定にしない。

人物の動作と外部effectを内部で分ける場合も、LLMが生成した文を所定の順で既存EMDへ載せればよい。翻訳・Compilerに新しい創作責務は持ち込まない。

## 6. 8Bでの検証計画

まず動画全曲生成ではなく、同じ8B GGUFで数区間のPlanner出力を比較する。新旧モデルの比較より、同一モデルで契約を変えた差を先に測る。

| ケース | 検証したいこと | 不合格例 |
|---|---|---|
| 苔へと還る | 苔の具体的な支持面・材質・変化、又は一度の適切な接触がある | 名詞だけ、手上げだけ、全Sceneで撫でる |
| 人は花より短く咲いて | 花と短命の意味を、揺れ・開花・散り等の一つの出来事へ展開する | 花を持つことの強制、無関係な発光 |
| 御神木は／ただ葉を鳴らすだけ | 境界を越えて同じ木の枝葉の動きを解釈する | 主語消失、一般的な身体揺れへの置換 |
| 朱の空に舞う狐火へ問う | 狐火自身の空間軌道、環境への結果、必要なら短い人物反応 | 毎回手に保持、身体部位が発光 |
| 対象語のない区間 | 苔・花・狐火・灯籠を勝手に主役化しない | 直前の対象への再接触・コピー |

この表の語は回帰試験の素材であり、本番プロファイルの語彙辞書にはしない。未知の具体名詞でも、同じ対象選択と具体化ができるかを追加で確認する。

比較条件は、GGUF hash、llama.cpp環境、chat template、温度、seed、n_ctxを記録して固定する。最初は同じ入力・seedで現行とP0のみを比較し、次に前後文脈／出来事単位を加える。改善が見えた後に2〜3 seedで再現性を確認する。token予算は実測の打切りがある場合にだけ段階別に調整する。

記録するもの:

- 実際のsystem prompt、payload、raw response、採択候補と修復理由。
- 根拠選択→具体化→Action→EMDのどこで対象・出来事が失われたか。
- 具体対象の描写率、出来事の成立、区間外漏洩、反復、推論回数・token数・所要時間。
- 独立effectを人物の手へ回収せず表現できたか。

既存ノードの`save_debug_output`と`trace`にはtask／payload／responseを残す仕組みがある。まずこれを使い、不足する採択理由だけ追加する設計でよい。

なお、`test_automatic_cue_reaches_actions_without_profile_dictionary`は`FakePlannerBackend`が御神木のCueとActionを返すテストであり、転送経路の検証である。テスト成功は8Bがその文を実生成できた証拠ではない。構造の単体テストと、実LLMの少数ケース評価を分ける。

## 最終判断

問題を「8Bには無理」と捉えるより、**8Bが既にできた連想を、現行の分業・制約・時間分割が生かせていない**と捉える方が、確認できた証拠と整合する。ただし各要因の寄与率はA/B検証前には確定できない。

最初の変更は、監査増強ではなく「歌詞に根拠を持つ創作的補完の許可」「独立effectの主役化」「文意を切らない局所文脈」「一つの出来事を継続して撮る」という四点に絞る。これなら外部仕様を大きく変えず、AS ISを保ったままプロトタイプの長所を再導入できる。
