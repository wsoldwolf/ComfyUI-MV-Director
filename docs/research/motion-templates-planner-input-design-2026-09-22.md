# ユーザー定義モーションテンプレートのPlanner入力設計

2026-09-22

> **設計変更（2026-09-23）:** この文書の`motion_templates_emd`入力ソケット案は採用しない。ソケットは本番ノードへ追加されておらず、削除する配線もない。ユーザー固有のScene演出候補は既存Direction Enhancer `user_request`内の`# 演出候補`セクションへ箇条書きで指定し、Direction artifactを通してPlannerのScene解釈へだけ渡す。旧一行形式は受け付けない。以下は比較検討時の旧案として残す。

## 結論

実現可能。ただし、候補を全Shotへ一律に渡すだけ、または有限IDをSceneごとに選ばせるだけでは、今回の目的である歌詞に合った連続的な振付は保証できない。候補は**Scene単位の任意の着想**とし、LLMが歌詞、Cue、Sceneの場所・対象、前Sceneからの姿勢、Shot構成を見て、一つの身体経路を選択・改変・新規作成するのがよい。そのScene固有の経路を既存のScene SpineとActionへ渡し、全候補を各Action呼出しへ繰り返し渡さない。

Pythonによる「監査」は、番号の範囲、応答形式、空欄、キャッシュ同一性といった機械的契約までに留める。歌詞との意味的適合をPythonの語彙規則で採点・修復しない。候補が合わない場合にLLMが独自の動きを考案できる余地を残す。これはAS IS原則と将来のモデル交換に合う。

## 現状から分かること

- `profiles/motion/anime_choreography_mv.md`の`# 振付候補`は、バッククォートで囲んだIDと本文の組である。`core/direction/profile_loader.py`は2件以上、各本文512文字以下、`scene_choice`又は`scene_palette`という条件で読み込む。候補はプロファイル固定で、ワークフロー実行ごとには変えられない。
- `scene_choice`はSceneごとの追加LLM呼出しで候補IDを選ぶ。既存の全編8B試験では16 Sceneすべてが`quiet_refrain`に偏った。前候補の機械的排除は多様性を作れても歌詞適合を示さない。
- 現行の`scene_palette`は追加選択callを使わず、全候補をScene SpineとActionに渡す。全編Planは完成したが、16 Scene・29 Shotでissue 129、反復警告47。鳥居上部への接触、「花壇の苔」、狐火の上に立つなどの空間的な不整合が残った。候補一覧を与えるだけではSceneごとの解釈は確定しない。[既存試験](choreography-operational-full-run-2026-09-22.md)参照。
- Plannerは既に`concept_emd`、`scene_emd`という接続専用の複数行STRING入力を持ち、入力内容とプロファイルをキャッシュキーに含める。ワークフロージェネレーターにも`PrimitiveStringMultiline`の既存例がある。新しい接続の形はこの経路を踏襲できる。
- `MVD_EMD_V1`の完成EMDは節の順序が固定され、Compilerは創作的な修復をしない。候補の節を完成EMDへ混入させると、Compiler/H3への漏出又は仕様拡張が必要になる。今回は**Planner入力専用のEMD断片**として仕様化し、完成EMDには残さないのが小変更で済む。

## 提案する入力契約

Plannerに任意の`motion_templates_emd: STRING`入力を追加し、ComfyUIのMulti Line String出力を接続する。本文は以下とする。

```markdown
# モーションテンプレート
* 始点は両足で安定し、片手は体側、もう片手は肘を曲げて低く置く。片側へ短く荷重し、骨盤の移動より遅れて胸郭を斜めへ向ける。低い手を視線の先へ弧状に差し出し、反対の腕は肘を緩めて釣り合いを取る。差し出した手を開いたまま一拍止め、呼吸と視線を戻し、両足支持で静かに収める。物を持つ・渡す動作は歌詞に明示された時だけ。
* 始点は膝を伸ばし切らず胸郭を正面に保つ。後ろ足から前足へ短く荷重を移し、骨盤が先行して胸郭が遅れて起きる。片腕は体の横から斜め前へ通し、もう一方は低い位置で反対方向へ開く。顔を上げて歌唱口を見せ、一拍のアクセント後、肩と肘を緩めて前足支持で終える。移動を伴う歩行や人物の全身回転にはしない。
```

解析は一つの`* `行を一候補として、原文の順序・自然文を保持した配列にする。`passing_memory`等の意味付きIDは不要。内部の一時的な1ベース番号はLLM応答の照合とログにだけ使い、EMD/H3へは出さない。空入力・未接続は現在のPlanner経路へ戻す。見出ししかない入力も候補ゼロとして扱う。一方、候補を記入しているのに見出しや箇条書きが壊れている場合は、黙って候補を捨てず、入力エラーを示す。候補1件を許す。文字数・件数は16k contextを見て事前計数し、超過時には切り捨てず明示する。

本節は`docs/spec/emd-spec.md`に「Planner専用入力断片」として追記する。Scene/Shotを含む完成EMDの節順とCompilerの文法は変えない。`anime_choreography_mv.md`からはトークン付き候補を外し、Motionプロファイルには動きの一般方針だけを残す。ユーザー入力とプロファイル内候補を連結しない。未入力時に既存のプロファイル候補を残すか完全に撤去するかは実装時に明記するが、推奨は**候補の単一供給源をユーザー入力に統一し、空なら通常の自由生成**である。

## LLMへの適用方法

1. 歌詞とCueから決まったSceneの出来事・対象・場所を先に固定する。テンプレートは物や環境を増やす根拠ではなく、身体経路の着想に限定する。
2. Scene単位で、候補群、歌詞、Cue、前Scene終端姿勢、Shot数とcoverageをLLMに見せる。LLMは候補をそのまま使う、Sceneに合わせて変形する、又は候補を使わず独自生成する。特定の候補の均等利用や毎Scene選択は要求しない。
3. LLMが作った**そのScene固有の短い身体経路**を既存のScene Spineへ渡し、複数Shotの始点→進行→終点へ分配する。ActionにはScene Spineの結果だけを渡す。単一Shot又はScene Spineが適用されないSceneではActionへScene固有の経路を渡す。
4. テンプレート本文を完成EMDのShotへ機械的に挿入しない。支持足、向き、歌詞との適合や前Sceneからの継続が崩れるためである。最終EMDの自然文はLLMの採用結果をAS ISで保持する。

実装候補は二つある。**A: 既存のScene Spine呼出しに候補を与え、同じ応答でScene固有の身体経路を生成する**方式は追加callが少なく、5060向き。ただし単一Shotの別経路が必要で、候補を本当に利用したか観測しにくい。**B: Sceneごとに短い選択・適応callを一回追加し、候補番号又は自由生成と身体経路を返す**方式は追跡しやすいが、呼出し数とcontextを増やし、既存の`scene_choice`と同じ偏りを起こし得る。現時点ではAを先に小区間で比較し、AでScene内の動きが連結しない場合だけBを試す。いきなり全曲へBを導入しない。

「LLMが候補を順位付けしPythonが選ぶ」方法は、Pythonが上位の**形式的に有効な**候補を採る場合に限れば成立する。しかし順位の意味的妥当性は結局LLM依存で、8Bの選択偏りも解決しない。順位付けだけを新設して自由生成を禁止する設計は推奨しない。Pythonが自然文にスコアを付けたりテンプレート本文を書き換えたりする方式は採らない。

## リスクと観測点

- 候補が長いと、Scene SpineやActionへの繰返し添付で`n_ctx=16384`を超える。全候補はScene単位の一箇所にのみ渡し、選択後は短い経路だけを伝播する。推論前の正確なトークン計数と超過ログが必要。
- LLMが特定候補へ偏る可能性がある。選択番号だけでなく、Scene間の支持・体幹・腕の流れと反復を観測する。頻度をPythonで均すのは避ける。
- 候補文中の「物を持つ」等が歌詞と無関係に具現化する可能性がある。Cueの対象・接触許可を優先し、候補を場所・小道具・effectのソースにしない。これはテンプレートの自然文を削除する処理ではなく、LLMへの役割説明である。
- `motion_templates_emd`の正規化した本文をPlannerキャッシュキーへ入れ、空欄と入力ありを区別する。変更後に古いPlanを再利用しない。ログには候補数、採用方式、Scene、fallback理由を記録し、本文を大量に出さない。
- `anime_choreography_mv`以外のMotion profileで入力した場合の適用可否を明示する。最小実装では`dance_phrase`で有効とし、他profileでの黙った無視を避ける。

## 実装前の低コスト検証

1. パーサーとキャッシュの単体試験：未接続、空、見出しのみ、1件、複数件、CRLF、壊れた箇条書き、長文、ユーザー入力変更によるcache missを確認する。
2. 保存済みの歌詞・Cue・Scene構造を使い、単一Shot、複数Shot、歌詞に具体物があるScene、静かなSceneを各1件ほど固定して8BのオフラインPlanを比較する。基準は候補なし、現行palette、新しいScene局所方式A。seedと生成条件を固定し、必要なら別seedで再現性を見る。
3. EMD上で、Scene始点と終点のつながり、Shotをまたぐ体幹・腕・視線の進行、歌詞対象の空間的整合、同じ候補の反復、顔Shotでの歌唱口、推論call数・時間・context使用量を記録する。候補番号が分散しただけでは合格にしない。
4. Aが明確に改善しない場合のみBを試す。EMDの身体連鎖が改善するまで全編H3レンダリングへ進まず、動画評価はユーザーのレンダリング結果で行う。

この時点では設計評価であり、新入力、仕様又はワークフローの実装は行っていない。
