## 3. 実装と対応づけた原因

### 3.1 「terminal」という名前だが、内容は完了した動作の全文

[scene_author.py](../../core/planner/scene_author.py)はScene末尾に次を保存している。

```python
previous_terminal = {
    "event": scene_event,
    "performance": action_texts.get(last, ""),
    "camera": camera_texts.get(last, ""),
}
```

この `performance` は終端姿勢の要約ではなく、末尾Shotの開始・移動・視線・歌詞反応を含む全文である。Cameraも到達構図ではなく経路を含む全文。さらに出来事・演技・Cameraの三担当すべてが、同じ三要素の辞書を受け取る。

| 担当 | 現在受け取る過去情報 | 本来の主な用途 |
|---|---|---|
| Event | 前の出来事＋人物動作＋撮影全文 | 現在見えている対象・継続中の現象だけを把握する |
| Performance | 同上 | 前の支持・位置・向き・手の状態から、新しい歌詞を演じ始める |
| Camera | 同上 | 前の到達画角・位置・旋回方向を引き継ぐ |

前の文は命令形・動作文なので、「今どうなっているか」という短い状態よりも、再利用できる完成回答として目立つ。8Bがそれを再提示する傾向は今回の出力に現れている。履歴が唯一の原因かどうかは、入力を変えた対照試験が必要である。

### 3.2 合成済み演技を履歴へ戻している

同実装は、Cameraへ渡すために次を実行する。

```python
action_texts[target] = action_texts[target] + " " + composition[4]
```

その後、同じ `action_texts` から `previous_terminal` を作る。補完対象が末尾Shotの場合、補完全文が次Sceneの三担当へ直接戻る。

Rendererは `content.actions` の原文と `motion_compositions` を別々の演技行へ出すため、データ上の出所分離は保っている。しかし一度LLMが過去の合成文を新しい原文に複写すると、その区別だけでは累積を防げない。

単に履歴へ戻す直前に文字列から補完文を削る案も適切ではない。既にLLMが言い換えて取り込んでいる場合があり、補完が変えた実際の位置・支持も失われる。必要なのは、**完了した指示の原文と、合成後に到達する状態を別に持つこと**である。

### 3.3 歌詞と候補はあるが、Eventが背景の説明へ退避している

Directionでは次を確認した。

- Motion：`anime_scene_composed_mv`。
- Camera／Style：`anime_emotional_mv`。
- ユーザー演出候補：7件。大樹の根元の苔、手に呼応して周囲を回る狐火、身体フレーズ5件。
- Motion指示は支持・重心・体幹・腕・表情の連動を含む。

実装はSceneの原歌詞と該当セクションの歌詞文脈、候補全文をEventとPerformanceへ渡す。したがって、最初から歌詞・候補を渡していないという説明は支持されない。

一方、Eventは前の三担当の全文、人物の詳細、環境説明等も受け取る。現在の歌詞から新しい出来事を選ぶより、既にある紅葉・鳥居・光を使い続ける出力になっている。これは入力の競合・過去回答への偏りという仮説であり、各要素の寄与は未分離。

Event promptは「外部物体又は環境現象の可視変化」を要求する。既にある苔へ人物が触れるだけの演出では、対象が変形しないため、その責務の説明が狭すぎる可能性もある。**人物との距離・関係や、見えていなかった対象が見えるようになる変化も、出来事として扱える**説明へ見直す。ただし狐火も欠落しているため、これだけが今回の原因ではない。

`# 演出候補` は任意候補であり、不採用自体は構文違反ではない。選択されないことを強制的なエラーに変えず、歌詞と候補が選択に使われたかを調べる必要がある。

### 3.4 新経路へ切り替わり、旧経路の機能は自動継承されない

[engine.py](../../core/planner/engine.py)は `performance_mode=scene_author` の場合、旧song-direction、Cue、scene-spine、品質監査、有限Camera処理より前に分岐して戻る。

このため、Scene authorへの切替は補完三文だけの追加ではない。簡略化したEvent/Performance/Camera経路を使う変更でもある。今回の結果を「従来の良かった苔・狐火へ三文を足しただけ」と比較してはいけない。

Camera profile本文はDirectionにあり、新経路もCamera担当へ渡す。一方、旧経路の `arc_roll_policy` に基づく選択処理などは実行しない。Rollが0であることは「profile全体が渡っていない」証拠ではなく、本文の指示とPython側policyの扱いが経路間で異なる問題である。

Plannerキャッシュは `typed_output=true`、`issue_count=0`、再試行Sceneなしだった。これは行プロトコル上の完了を示す。新経路では旧品質監査を通っていないため、形式成功から創作品質を推定できない。

### 3.5 旧プロトタイプの三文を使っても、挿入条件まで同じではない

[旧関数の保存原文](../assets/research/legacy-action-2026-09-23/provenance/manifest.json)では、`repair_lyric_action_motion` が不足する身体phaseを求め、不足があるときだけ固定文を追加する。元の歌詞Actionを残して後続phaseに置き、既存行へ結合する場合には「続いて」を使う処理もある。

現[補完選択](../../core/planner/motion_composition.py)は、4秒以上・作者固定なし等の条件を満たす最長ShotへScene番号で巡回して一文を追加する。身体演技の不足・出来事への適合・前後の順序は判定していない。

三つの旧文は主に大きな位置移動であり、その場の支持移動・体幹・腕・表情を組み合わせる振付候補とは異なる。現方式で移動量が増えても、身体演技の多様性が増えるとは限らない。

旧版の語彙判定をそのまま増設するのではなく、歌詞対象との両立と時間順の合成を最小限の契約として検証する。旧動画がこの補完だけで良くなったという因果は、依然確定していない。

## 4. 前回の短区間試験で見逃した理由

[前回](motion-composition-2026-09-23.md)の実8B試験は、保存済みScene 5・9をそれぞれローカルScene 1へ置き換え、単独生成した。したがって次が試験外だった。

1. 前Sceneから完成文を受け取る状況。
2. 一度足した補完が、次SceneのLLM原文へ入る状況。
3. 第2・第3テンプレートの作用と、三種類の累積。
4. 実運用の詳細な人物・背景、7件のユーザー候補。
5. 既存セクション全体と連続した複数Sceneの流れ。

CPU試験は原文保持、作者優先、Cameraへの補完伝達、キャッシュ、EMD再入力時の二重追加防止を確認していた。継続試験も「過去本文が渡る」ことを期待しており、その本文が生成を固定化しないことは確認していない。

**単独Sceneでの合成成功と、全曲で安全に使えることの間に検証の空白があった。** テスト件数を増やすより、この実運用の連鎖を一つの試験対象にする。

## 5. 次の計画

### P0：出典・入力・反復の再現条件を固定する

本報告で確認したEMD、採用キャッシュ、Directionを次の比較用fixtureへ固定する。可変なComfyUIの出力番号や最新WFだけに依存しない。

- 元のScene番号、歌詞、時刻、Shot長、継続を保持する。Scene 1へのリベースは避ける。
- 手書き演技と生成演技を区別し、元のTemplate／provenanceから未生成入力を復元する。完成EMDの全本文を無差別に消して作者指定を失わせない。
- 三種類の補完、候補7件、人物と背景、system/profileのhashを保存する。
- 実験では各呼出しの要求、原応答、採用文、補完、次へ渡した状態、token数、実効seedを記録する。
- 比較は同一のモデル・設定で行い、対応するScene／担当の呼出し間では実効seedを固定する。入力変更でseedまで変わる通常のpayload依存方式は比較時に使わない。現在の全編キャッシュは観察基準として使い、実効seed不明の厳密な対照とは扱わない。

CPUでは、前Sceneの補完と同じ文を返す模擬backend、補完を少し言い換えるbackendを用意する。単なるEMD再入力の二重追加防止と、生成中のScene間累積を別の現象として検証する。

### P1：担当ごとに履歴を分け、指示の全文から終端状態へ移す

最初の比較改修は新 `scene_author` 経路内に限定する。

- **Event**：現在の歌詞・候補と、持続している対象の状態を中心にする。前の人物動作・Camera全文を入力から外す。歌詞にある対象を見せる、距離や関係が変わる、外部現象が生じる、という選択を可能にする。
- **Performance**：前Sceneの位置・支持・体幹／腕・視線の終端状態から、新しい歌詞の演技を始める。前の動作列や補完文そのものを次の命令として渡さない。
- **Camera**：前の到達構図・視点・旋回方向と、今回の合成済み演技を受け取る。過去の撮影経路の全文を再提示しない。

終端状態をPythonの正規表現で自然文から推測しない。必要な状態は既存の各担当の応答に短い内部レコードとして同時出力させる。新しい要約LLM段は追加しない。

初期案は各担当一つの `END_STATE`。自由な短文で、担当に応じた終端だけを記す。Eventは対象の存続状態、Performanceは補完後を含む身体の状態、Cameraは撮影の到達状態と旋回方向を担当する。補完予定をPerformanceへ先に伝える既存経路を使い、合成後の終端もそこで計画する。

これは追加のLLM出力項目なので、まず実験用grammarで形式と短文生成の安定性を確認する。初期出力目安は担当ごとに一、二文。具体的なtoken上限は実測で決める。空状態を許容し、欠落を埋めるために過去の全文へ無言で戻さない。内部状態はEMDやH3へ出さず、採用演技原文・補完の出所と別保存する。

状態を短くしても姿勢接続が弱くなるリスクはある。したがって「再演しない」と「前後がつながる」を別々に評価する。短くなったこと自体は合格条件にしない。

### P2：補完の選択・時間上の関係を整える

P1で反復が改善してから進む。現在の三文の巡回は比較用baselineとして保存する。

最初は**選択した一文を一度だけ使い、原演技との順序を明示できるか**を検証する。補完文を単に二つ目の演技行へ置くことは「後半に行う」の保証にならない。Performanceが同じShot内の準備・補完中の腕や表情・終端を計画し、Cameraもその時系列を読む形を試す。

次に、既存Event又はPerformanceの呼出し内で、候補番号と使用Shot／使用なしを選べる案を比較する。補完は作者・profileにある原文を合成し、Pythonは選択ID・Shot範囲・重複実行の有無だけを検査する。苔や狐火の単語辞書で動作を割り当てない。

接触中の手を離す前に横方向へ加速する、といった不整合はLLMが計画時に避ける。品質違反を何十回も監査する仕組みへ戻さない。意味的に不自然な候補は比較の不合格として記録し、実験が改善しなければ昇格しない。

`# 演出候補` は引き続き任意の着想、`# モーション補完` は明示的な合成許可として区別する。ユーザーの固定 `演技`・`カメラ`・継続指定は最優先。profile側の実験方針で切り替え、入力ソケットやUI項目を増やす必要はない。

### P3：採用演技にCameraを合わせ、全編EMDから短いH3確認へ進む

Cameraは今回の身体フレーズの主動作・アクセント・終端を具体的に撮る。大量のCamera規則を重ねる前に、次を確認する。

- Arc中の身体移動と相対位置が成立し、連続区間で急な逆旋回がない。

よって「長い全文履歴が反復を促す」という仮説は支持されたが、**短い自由文状態へ置換するだけでも、状態を全面廃止するだけでも、MV演技の実用改善にはならなかった。** Scene継続はTemplate上15/15保持しているが、EMD上の身体・対象の連続性までは証明しない。P0の固定とP1の実装・反証実験は完了し、P1の品質採用は保留する。P2のモーション候補選択とP3のH3映像比較は、当初のゲートに従い実施しない。
