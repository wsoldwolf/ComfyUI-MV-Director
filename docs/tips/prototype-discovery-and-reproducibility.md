# 試行錯誤で生まれた良さを、仕様化したシステムへ移す難しさ

2026-09-23。本プロジェクトの開発経験に基づく考察。

## プロトタイプは、結果を見ながら継ぎ足して作られた

ComfyUI-cl-japanese2jsonは、いわゆるバイブコーディングによって、
生成結果を見ながら指示・補正・例外処理を継ぎ足して作られたプロトタイプである。
設計が初めから整理されていたわけではないが、身体演技やCamera連動に魅力のある動画を生成できた。

現行プロジェクトでは、仕様、行protocol、役割分担、原文保持、テストを整備しながら実装してきた。
この方法は構造と変更理由を説明しやすくする一方、プロトタイプの良い表現を自動的に引き継ぐものではなかった。
**仕組みを整理して作り直すことと、完成映像の良さを再現することは別の課題だった。**

## 「何が効いていたのか」を後から調べる費用

良い動画だけが残っていると、その理由をLLMの能力、システムプロンプト、歌詞の扱い等へ帰したくなる。
しかし実際には、次の要素が重なっている。

- 歌詞をどのまとまりで渡し、どの述語を演じさせたか。
- LLMの素の応答と、再試行・補完後に採用した文章の違い。
- Pythonによる全身動作の追加、Camera補完、Shotへの再配分。
- H3へ渡した共通promptと局所prompt、その順序と長さ。
- モデル、量子化、chat template、seed、参照画像、継続設定。
- 映像生成モデルが文章に明記されていない動きをどのように補ったか。

今回、旧EMDにある強い全身移動の一部はPythonの三種類の固定文と一致した。
「同じ8Bなのだから、旧LLMと同じ入力をすれば同じ振付が出るはず」という比較にも、
後処理まで含める必要があった。詳しくは[機械的な補完と演技](mechanical-motion-and-perceived-performance.md)を参照。

旧コードに説明しにくい補正があったとしても、それが良い結果に寄与していた可能性はある。
整理の際に削除すると、コードは理解しやすくなっても、その働きを別の場所で再実装する必要が生じる。
寄与を確かめずに再設計すれば、何度も長時間の動画生成を行いながら原因を探すことになる。

## バイブコーディングと仕様化を勝ち負けにしない

この経験は、バイブコーディングの方が常に優れている、あるいは仕様化が無駄だという主張ではない。

試行錯誤は、事前に言語化できない表現を発見しやすい。
仕様化は、その発見を再利用し、変更の影響を限定し、ユーザーが操作できる機能へ変えるために役立つ。
難しいのは、**発見段階で成立した複数要素の組合せを、移行時にほどいてしまうこと**である。

正しいprotocolで完了することは必要だが、それだけでは「生き生きしている」という品質を測れない。
同様に、偶然うまくいった動画一本だけでは、他の曲でも安定して再現できる設計とは言えない。
両方の性質を分けて記録する必要がある。

## 次のプロトタイプで残しておきたいもの

1. **良かった完成動画と、実際に採用したPlan。**
   LLM入力だけでなく、補完・翻訳・配分後のH3入力を保存する。
2. **生成段階ごとの原文と出所。**
   LLM原文、ユーザー指定、固定文補完を区別する。成功結果だけでなく失敗と再試行も残す。
3. **環境と実効設定。**
   commit、prompt/profile、モデル識別、seed、chat template、sampling、生成モデルを記録する。
4. **変更を一つだけ戻せる比較条件。**
   補完の有無等を切り替えられるようにし、全編ではなく短区間から確認する。
5. **人間が良いと感じた理由。**
   何秒付近の重心移動、切り返し、視線、Camera連動が良かったかを言葉で残す。

新機能を最初から大きな仕組みにせず、発見を小さい切替可能な契約にして保存する。
今回のモーション合成も、そのための試みである。

## 今回の教訓

「継ぎ接ぎで良い結果が出たもの」を「整理した実装で再現可能な機能」へ変えるには、
最初の試作とは別種の調査と検証が必要になる。
特に長時間の動画生成を伴う本プロジェクトでは、その費用と疲労は小さくない。

原則は保守のために重要だが、原則だけで成果を評価しない。
良い結果の理由を追跡し、必要なら例外を明示して仕様へ取り込み、
ユーザーが有効化・変更・無効化できる形にする。
それが今回のAS IS原則を限定的に見直した理由である。
