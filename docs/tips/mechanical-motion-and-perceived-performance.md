# 機械的な補完文が「演技」に見えること

2026-09-23。プロトタイプとの比較で得られた発見と、明示的なモーション合成を試す理由。
詳細な実験条件は旧8B再現レポート（外部研究アーカイブ: `legacy-action-replay-2026-09-23.md`）を参照する。

## 発見：豊かな映像の全てが、豊かなLLM出力から生まれたわけではない

ユーザーは、プロトタイプの映像に、現行版より生き生きとした身体演技を感じていた。
調査すると、復旧した旧環境のEMDにはPythonが追加した次の三種類の固定文があった。

1. 人物は現在の形状と外観を維持したまま、身体全体を連動させて画面内を斜め前方へ大きく移動し、その方向へ動き続ける。
2. 人物は現在の形状と外観を維持したまま、身体全体の向きを変えながら横方向へ加速し、別の位置へ移動を続ける。
3. 人物は現在の形状と外観を維持したまま、身体全体を後方へ大きく退かせた直後に前方へ切り返し、異なる軌道で移動を続ける。

実装上の人物表記は `<Subject 1>` 等の参照だった。ここでは読みやすく「人物」とした。
歌詞の内容に合う文章をその都度生成したのではない。
身体動作が不足した際に、Scene番号を基準に三文を巡回選択していた。
保存された復旧版EMDでは、Scene 6・8・9・11・12に合計9箇所の一致を確認した。

旧8Bの前段を現在の環境で再実行すると、口・眉・手の上下に偏った出力も多かった。
旧版の良好な完成映像を見て「LLMが自然な振付を全て書いた」と推定するのは早計だった。

ただし、ここで確認できた事実と、まだ仮説であることは分ける。

- **確認済み：** 旧コードに固定文補完があり、復旧版EMDにそれが入っている。
- **ユーザーの映像評価：** プロトタイプの身体演技は生き生きして見えた。
- **未検証：** 同一条件で固定文だけを除いたH3動画との対照比較。
- **断定しないこと：** 固定文がLLM文章より常に自然である、又は旧動画の良さは補完だけが原因である。

9月12日の動画と復旧版EMDは、同一の生成入力と確認できていない。
Camera、共通prompt、参照、生成モデル、継続時間、sampling等の差も残る。

## なぜ単純な文から演技が見える可能性があるのか

次は映像生成の働きに関する仮説であり、今回の因果検証結果ではない。

### 1. 大きい運動の指示が、細部をモデルに委ねられる

「後退して前方へ切り返す」は短いが、時間順序と方向変化がある。
H3がそれを実現する際、足の踏み替え、上体の遅れ、腕の釣り合い、衣装の動き等を補う可能性がある。
関節ごとに細かく説明しなくても、一つの全身運動としてまとまる余地がある。
ただし、足滑りや不自然な移動として現れる可能性もある。

### 2. 速度・移動量の変化が、表現の強弱になる

腕を上げるだけの文と比べ、加速や切り返しには見た目の変化が生まれやすい。
音楽、表情、Cameraの移動と組み合わさると、その変化を人間が感情として読むこともある。
これは「歌詞に忠実な動作の説明」と「MVとしての説得力」が同一ではないことを示唆する。

### 3. 自然さは一つの部品ではなく、組合せから現れる

LLMが出来事と表情を作り、Pythonが身体運動を補い、Cameraが追い、H3が中間動作を描く。
その全体が良ければ、各部品が単純でも演技として見える可能性がある。
反対に、各文章が詳しくても、同時に静止と移動を要求すれば全体は破綻する。

## AS ISの見直し

「Pythonは自然文を一切加えない」という境界は、出典とデバッグを明確にする利点があった。
一方、それ自体が映像品質を保証するものではなかった。
そこで、LLM原文を保持したまま、**作者又はprofileが明示したモーションだけを別行で合成する**
限定的な例外を設けた。

現在の比較用実装は次の範囲である。

- Motion profile `anime_scene_composed_mv` で旧三文を比較する。既存profileは変更しない。
- `# モーション補完` は機械的合成の許可。`# 演出候補` はLLMが採否を選ぶ候補であり、別の意味を持つ。
- 単一人物・全自動演技のSceneで、Camera未固定かつ4秒以上の最長Shotへ一文だけ追加する。同尺なら先のShot。
- Scene番号で候補を巡回選択する。演技品質の正規表現判定は新設しない。
- 手書きの演技又は一般本文があるSceneは追加しない。ユーザーの共通Motion上書き時もprofile補完を抑止する。
- 補完予定を演技LLMへ知らせ、原文＋補完文をCameraへ渡す。
- 原文と補完文を分けて保存し、EMDにsource・候補番号・hash、INFOに適用箇所を記録する。

この選択法が歌詞の感情に最適とは限らない。意味衝突を自動解決する仕組みではなく、
有効化した作者が候補内容を管理する、最初の比較実装である。
通常の手書き優先や、Compilerが演出を発明しない原則は維持する。

## 実際に試す方法

Direction EnhancerのMotionを `anime_scene_composed_mv` にする。ComfyUI再起動後、
Enhancerから再実行する。人物や背景の画像を変更する必要はない。
既存WFの既定profileは自動変更しない。

ユーザー入力でprofileの三文を置き換える場合：

```markdown
# モーション補完
* 人物は両足で支え、重心を左から右へ短く渡す。胸郭を遅れて追従させ、片腕を斜め前へ通し、反対の腕で釣り合いを取りながら姿勢を収める。
* 人物は膝を軽く緩めて重心を落とし、胸を起こす動きに合わせて左右の腕を異なる高さへほどき、視線を正面へ戻す。
```

これは歌詞に合う時だけ選ばれる任意候補ではなく、適格Sceneへ巡回合成する動作一覧である。
苔や狐火等の条件付きの出来事は、従来どおり `# 演出候補` に記述する。

無効化は次のとおり：

```markdown
# モーション補完
* 無効
```

省略はprofileから継承、`無効` は明示停止。両者を区別する。
上限12件、各500文字。全文を全Sceneの共通promptへ投入しない。

## 今回の短区間試験から

Scene 5・9で合成あり／なしを試し、4件ともEMD生成は完了した。
合成ありのScene 9では、斜め移動に腕を伴わせ、次Shotで止まって視線を移す応答が出た。
Scene 5では合成してもLLM本文の反復が残った。
補完なしScene 5にはエスケープされた行protocolの本文混入も見られたため、良好な対照映像用素材とは扱わない。

これは「動作を確実に渡す経路ができた」という確認であり、自然な動画が実証されたわけではない。
映像の自然さとCamera同期は、次の短区間レンダリングで判断する。
失敗を固定文の追加量で覆い隠さず、元の演技・合成文・映像を別々に記録する。

追加で、要求payloadに依存したseedの変化を除き、全呼出しの実効seedを固定して比較した。
Scene 5では、補完される移動と同じShotに「身体は静止」とLLMが書く競合が残った。
Scene 9は前進と腕の動きが出たが、前傾・歩行への偏りもある。
この結果からも、合成機能の動作確認と映像品質の達成を区別する必要がある。
