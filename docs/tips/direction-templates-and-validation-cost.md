# 演出テンプレートという選択肢と検証負荷

本稿は現在の仕様を定めるものではなく、MV演出をLLMへどこまで委ねるかを考えるための設計上の考察です。

## Motion / Cameraを選択式にする案

現在のPlannerは、歌詞、Direction、人物・背景情報及び履歴からSceneごとのActionとCameraを生成します。この方法には、歌詞固有の対象や感情を拾い、事前に列挙していない演出を作れる利点があります。一方、小型LLMでは同じ身体動作の反復、Camera protocol違反、演技と構図の不一致が起こり得ます。修復や監査を増やすほど推論時間も長くなります。

そこで、ユーザーが「上半身のためらいから解放へ」「手を対象へ伸ばして離す」といったMotionテンプレートと、「長いArcから顔へ寄る」「顔からArcで全景へ抜ける」といったCameraテンプレートを選び、その組合せをCompilerがH3 promptへ変換する方式も考えられます。期待する演出を直接選べるため、結果の予測、再利用、比較及び不具合の切り分けは容易になります。LLMには歌詞の意味に合う候補の順位付けや、対象・感情・強度の差し込みだけを担当させる構成も可能です。

ただし、テンプレート方式だけで問題が解決するわけではありません。

- 用意された演出へ表現が固定され、歌詞から生まれる意外性が弱くなる。
- MotionとCameraの組合せに加え、Shot尺、人物の向き、対象の位置、前後Shotの継続状態を検証する必要がある。
- テンプレート数を増やすと選択肢と組合せが膨らみ、保守対象が別の形で増える。
- 文章上は妥当でも、H3が人物の回転、手足の崩れ又は不連続なCameraとして解釈する可能性は残る。

現実的には、完全自動生成と完全な手動テンプレートの二択ではなく、併用が適しています。外部profileで演出セットを選び、Plannerは歌詞に基づいて候補を選択又は限定的に具体化し、Compilerは有限のCamera形式と参照契約を保証する、という責務分担です。ユーザーが明示的にテンプレートを選んだ場合はその意図を優先し、自動モードでは歌詞から選択する構成なら、再現性と発見性を両立できます。

導入を判断する場合は、まず少数の代表的な組合せだけで比較すべきです。テンプレートの数ではなく、同じ歌詞・Plan・参照画像を使った局所Sceneで、反復、演技の明瞭さ、Cameraの連続性及び再生成時の安定性が改善するかを評価します。

## Codexを使っても検証は軽くならない

Codexは、大量のコードと仕様を横断した調査、変更案の実装、回帰テスト、ログ・EMD・Planの照合及び文書化を高速に進められます。本プロジェクトでも、人手だけでは追跡が難しい複数段階の因果関係を整理するうえで大きな力になります。

しかし、Codexを使うことと、開発が楽になることは同義ではありません。とりわけ本プロジェクトは、短い単体テストだけでは品質を判定できません。Vision、歌詞整列、複数回のLLM推論、翻訳、H3による動画生成、連結及び映像の目視評価まで進めて初めて分かる問題があります。一回の全編生成に長時間を要し、修正後も乱数による差と実装による差を分離しなければなりません。待ち時間、GPU資源の管理、ログ収集、同じSceneの反復視聴及び判断の記録は、開発者に継続的な負担を与えます。

AI支援が強力であるほど、短時間に多くの変更案を作れるため、すべてを試したくなる点にも注意が必要です。生成できる変更量が、人間が映像を評価できる量を上回ると、検証待ちが新しいボトルネックになります。実装速度だけを上げても、評価基準と試験範囲が曖昧なら疲弊は減りません。

この負荷を抑えるため、本プロジェクトでは次の運用が重要です。

1. Plan / CompilerとVideoを分離し、後段の失敗で重い前段をやり直さない。
2. `Scene Debug Splitter`で問題Sceneだけを生成し、全編レンダリングは節目に限定する。
3. 一回の試験で評価する仮説を絞り、変更前後で同じ入力と対象区間を使う。
4. protocol回帰テスト、実8Bの局所試験、H3映像試験を区別し、前段の成功を映像品質の成功とみなさない。
5. 良かった結果と失敗した結果の両方をレポートへ残し、同じ試行錯誤を繰り返さない。
6. 長時間試験の連続実行を避け、判断が鈍った時は作業を区切る。

Codexの価値は、検証を不要にすることではなく、検証可能な変更単位を作り、観察結果を次の判断へ接続しやすくすることにあります。最終的な映像の良否は人間が見て判断する必要があり、その時間と集中力も計算資源と同じく有限のプロジェクト資源として扱うべきです。
