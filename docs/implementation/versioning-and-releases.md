# バージョン・ブランチ・リリースの管理

本プロジェクトのバージョン番号は、`major.minor.patch`の三つの数値で構成します。
Gitのブランチ名とリリースタグには接頭辞`v`を付けます。

## バージョン更新とブランチ

| 更新区分 | 番号の更新 | ブランチの扱い | 例 |
|---|---|---|---|
| patch | リリースごとにpatchを増やし、major・minorは維持する | 新しいブランチは作らず、同じ系列のブランチで更新する | `0.1.1` → `0.1.2`。ブランチは`v0.1.0`のまま |
| minor | minorを増やし、ブランチのpatchを`0`へ戻す | 新しい系列ブランチを作る | `0.0.x` → ブランチ`v0.1.0`。最初のリリースは`v0.1.1` |
| major | majorを増やし、ブランチのminor・patchをともに`0`へ戻す | 新しい系列ブランチを作る | `0.x.x` → ブランチ`v1.0.0`。最初のリリースは`v1.0.1` |

バージョン系列のブランチ名は`v<major>.<minor>.0`とします。
例えば`v0.0.0`、`v0.1.0`、`v1.0.0`です。patch更新ごとのブランチは作りません。
コミットを作るたびにバージョンを上げる必要はなく、バージョン更新とリリースの区切りで番号を決めます。

## リリースタグ

リリースするコミットに、完全なバージョン番号のタグを付けます。
例えば`v0.0.0`ブランチ内でpatch更新を進め、`0.0.1`としてリリースするコミットへ
`v0.0.1`タグを付けます。ブランチ作成だけではリリース扱いにしません。

**同じmajor.minor系列でリリースするたびに、原則としてpatchを1つ増やします。**
例えば`v0.1.0`ブランチの最初のリリースは`v0.1.1`、その次は`v0.1.2`です。
コード変更の大小にかかわらず、異なるリリースへ同じバージョン番号を再利用しません。
minor又はmajorを更新する場合は、系列ブランチの対応する下位番号を`0`へ戻します。
`.0`はブランチ名として予約し、新系列の最初のリリースタグには`.1`を使います。
したがって、ブランチ`v0.2.0`の最初のタグは`v0.2.1`、ブランチ`v1.0.0`の
最初のタグは`v1.0.1`です。

| 操作例 | ブランチ | リリースする場合のタグ |
|---|---|---|
| `0.0`系列を開始 | `v0.0.0`を作成 | `v0.0.1` |
| 次のpatchをリリース | `v0.0.0`で継続 | `v0.0.2` |
| minorを更新 | `v0.1.0`を作成 | `v0.1.1` |
| その系列で次をリリース | `v0.1.0`で継続 | `v0.1.2` |
| majorを更新 | `v1.0.0`を作成 | `v1.0.1` |

ブランチとタグは異なる役割を持ちます。ブランチはその系列の開発先、タグは
リリース時点のコミットを示します。`.0`をブランチ、`.1`以降をリリースタグに
使うことで、ブランチ名とタグ名の重複を避けます。

## このリポジトリでの運用

コミットは依頼又は作業範囲に含まれる場合に作成し、作成したコミットは
`origin`と`github`の両方へpushします。リリースタグも、リリース時に両方へpushします。
公開済みのタグを別のコミットへ付け替えてリリース内容を変更せず、修正版は新しい番号で扱います。

ルール導入前の履歴については、バージョン番号を推測してブランチやタグを追加しません。
最初の適用バージョンと起点コミットを決めてから、その系列のブランチを作成します。

本ルールはプロジェクトのリリース番号を対象とします。EMD・artifactのschema ID、
Plannerのcache用algorithm version及び外部H3の契約IDとは別に管理します。
